This is an unusually rigorous spec — the normative timing table in §0, the identity/placement split, and the discipline of stating *why* each rule exists (rather than just what it is) put it well above typical framework design docs. The strongest ideas are genuinely good: the shape/value rule as the single organizing distinction; the three mint-policy operations on the projector (`requireKey` throwing instead of silently promoting a runtime entity to document content is exactly the right call); the lagging baseline as an implicit drag detector with no gesture flags; and writer-partitioning as the move that lets the ephemeral layer *delete* conflict machinery rather than configure it. The Loro quarantine to two adapter classes is clean, and the cost honesty (tag probes are O(N·t), the per-chunk iterator allocation) builds trust.

That said, I found what I believe are real correctness problems, plus some domain-level gaps that matter for the stated Figma-like target. In rough priority order:

## Correctness issues

**1. The baseline compare breaks on value canonicalization — this is the most serious bug.** Reconcile's entire conflict model rests on `runtime(cell) == baseline(cell)`, but the two sides store values differently: the runtime rounds through typed arrays (`Float32Array` frounds, `u8` truncates, enums store discriminants), while the baseline is a plain in-memory map holding whatever `ComponentValue` object it was handed. Walk through a remote `component-set` of `Position.x = 0.1`: the projector writes the runtime (which stores `0.10000000149…`), and the baseline advances to `0.1` exactly. The cell now reads `runtime != baseline` *with no edit in flight* — so every subsequent remote value to that cell is dropped as "drag in flight," permanently, and the stranded-cell warning eventually fires on a cell nobody misused. The same applies to any transaction authoring a non-f32-exact literal, to int truncation, and to enum label-vs-discriminant ambiguity in `ComponentValue`. The fix is straightforward but must be normative: define a canonical `encode(v)` per field type, require every baseline write (and the doc-fact values reconcile compares) to pass through it, and define cell equality as field-wise equality of *encoded* values. Right now the spec never mentions this, and an implementer following it literally ships a broken reconcile.

**2. The conflict model silently depends on an unspecified Loro layout.** §13.4's guarantee — committer-wins per *whole component*, no field merge — is only true if `LoroSnapshot` stores each component value as one atomic register (a single map value assigned wholesale). If an implementer naturally models a component as a nested Loro map with per-field keys, Loro's per-key LWW will happily merge your `x` with their `y` — producing exactly the "position neither chose" that §13.4 promises can't happen. The document schema inside Loro is never specified anywhere; this needs to be a stated contract on the adapter ("a component is one atomic value; field-granular containers are forbidden"), because the correctness of the layer above depends on it.

**3. Remote structural changes crash in-flight local gestures via `edit().set`.** §17 covers the read side (use `get`, not `read`, for shared entities) but the write side has the same hazard and no mitigation: a remote `removeComponent(Position)` or despawn is structural, so it applies unconditionally at `sync()` mid-gesture (§13.3), and the next frame `DragSystem` calls `ctx.edit(target).set(Position, …)` — which *throws* if the component is absent (§5.3). Despawn is covered by validate-on-read (no-op), but component removal on a live entity is not. Notably, the worked example violates the spec's own §17 rule: `GestureRecognition` does `ctx.read(target, Position)` at pointerup on a stored, shared handle, and `tx.edit(target).set(...)` will throw at record time if the key is gone. Interaction code needs either a safe-write variant, a documented `has()`-guard pattern, or the example fixed to model the guidance — as written, the flagship example crashes the frame a collaborator deletes your drag target's `Position`.

**4. The `world.*` mid-tick guard is asserted in Part IV but contradicted in Part I.** §15.2 states as a general rule that "any mutation path that would corrupt active iteration throws in all builds — the runtime command-buffer discipline enforces the same thing for `world.*` structural ops issued mid-tick," and mentions an `isIterating` boolean. But Part I's `ECSStore` section says the opposite: `World` delegates straight to the store, mutations are immediate, and the store must never consult iteration state. Nowhere in Part I is a World-level mid-tick guard specified. Either the guard lives on `World` (not the store) and Part I must say so, or `world.addComponent` from inside a system body silently corrupts iteration. Given how carefully the rest of the timing model is pinned down, this is a conspicuous hole.

## Domain gaps for the editor target

**5. Ordered collections are accepted by the API but undefined — and the target domain needs them badly.** `defineRelation(..., { ordered: true })` exists in the signature, §3.3 explicitly says many-relations are unordered Sets, and the promised "dedicated tree/ordered-list index" is never specified. For a Figma-like editor, child order and z-order under *concurrent* editing is a famous hard problem (fractional indexing, CRDT movable lists — which Loro actually has). The example's `ZIndex { z: i32 }` workaround produces duplicate/conflicting z values under concurrency with committer-wins semantics. This is the single biggest functional gap between the spec and its stated use case, and it deserves either a real design or an explicit "out of scope, here's the recommended pattern."

**6. Collaborative text doesn't merge, and the spec doesn't say so.** `Label { text: "string" }` is whole-component LWW: two people typing in one text element clobber each other at commit granularity. That's a defensible v1 trade-off, but for a canvas editor with text it should be stated loudly, ideally with a forward path (e.g., an opt-in field type backed by Loro's text CRDT, quarantined in the adapter like everything else).

**7. Mixed schema versions on the wire are unhandled.** The migration note covers load-time upgrades, but live collaboration between peers on different schema versions is the harder case: what does reconcile do with a `component-set` whose `ComponentName` is unknown locally? The right answer is almost certainly "preserve in the document, skip projection, don't destroy on echo" — but it needs to be specified, or an older peer silently drops (or crashes on) a newer peer's data. Related: nothing validates inbound values against the schema (range, type, well-formedness), so a buggy or malicious peer writes garbage straight into typed arrays.

## Smaller notes

A few things worth a pass but not structural. The baseline is a full second in-memory copy of the document (third, counting Loro's state) — fine at editor scale but never acknowledged as a cost. Large inbound bursts (a late-joining peer importing a big document over the wire) reconcile in one `sync()` with no amortization story, which is a frame hitch waiting to happen. `undo()` is delegated to Loro without saying whether it's local-ops-only undo (it should be, in a collaborative editor — worth one sentence). Ephemeral peer-id hygiene: a *stable* peerId plus a reload inside the TTL window means the new session's `alice-0` collides with the not-yet-expired ghost of the old one; recommend session-unique ephemeral peer ids. `Entity` is a bare `number` while `EntityKey` is branded — inconsistent, and branding `Entity` would close the row-vs-handle footgun the spec itself works around (keeping `getRelated` off `ctx`). Tombstones are mentioned once in §17 and never defined. Drain order across multiple attached `InboundSource`s is unspecified. And there's no change-detection/reactivity story (a `Changed<T>`-style filter) — full-redraw is fine for a canvas, but UI panels bound to entity state will want it; worth stating as a deliberate scope cut. Finally, `Selection` in §18.1 uses `targetKey: "string"` when the spec's own §14.3 introduces the `"key"` field type for exactly this.

## Bottom line

The architecture is sound and the hard parts — the timing model, the projector, the reconcile matrix — are worked to a depth I rarely see. The four-part layering genuinely holds up: I went looking for dependency leaks and didn't find one. But issues 1 and 2 are ship-blockers hiding in unstated assumptions (value encoding at the baseline boundary, atomicity of the Loro component layout), issue 3 means the interaction layer as documented is fragile against exactly the concurrent operations the framework exists to handle, and issue 5 is a real feature gap for the declared domain. Given how invariant-dense this spec is, I'd also strongly suggest a companion conformance suite — many of the stated invariants (string columns null above `count`, batch atomicity, baseline-runtime lockstep) are directly property-testable, and that's the only way a spec this size stays true through implementation.
